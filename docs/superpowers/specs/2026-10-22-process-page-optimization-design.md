# 进程页易用性、可靠性与轻量化优化规格

- 日期：2026-10-22。
- 项目：WinMemoryCleaner Community，`community` 分支。
- 代码基线：`11afbfd0f366a50f298603d9926168fe35efb5b0`；已发布产品仍为 `v3.0.8.4-community.4`。
- 状态：首批对话设计已确认；书面规格提供后用户再次要求继续，现按此规格编写实施计划。产品实现尚未开始。
- 执行偏好：用户要求“直接干完就好了”，希望主代理连续完成实现、检查与收尾，不逐项询问常规技术决定。该偏好不替代书面规格及实施计划的审阅，也不授权实际驱动安装或覆盖用户程序。

## 1. 用户意图与首批范围

用户要求持续优化产品，并明确易用性、可靠性、轻量化都要覆盖。首批围绕现有进程页的“查找进程 → 查看占用 → 刷新 → 操作选定进程”工作流进行改进，而不是同时重写多个子系统。

本批成果：

1. 搜索反馈清楚：显示匹配数与总数，方便清空，区别加载、成功空列表、无匹配和读取失败。
2. 异常行为可靠：旧列表不能冒充最新数据；失败、筛选变化、进程退出或 PID 复用不能绕过操作入口的选择有效性检查。
3. 界面工作更少：快速输入合并处理，相同查询不重新筛选，相同或与当前排序无关的快照变化不整表重排。

### 保持不变

- 主程序保持 WPF、.NET Framework 4.0、C# 4；保留 `AllRules.ruleset`、既有九个分析器及 warnings-as-errors，不降低严格构建要求。
- 保留内存清理、托盘、设置、主题、语言、紧凑模式和校验更新行为。
- 保留横向/竖向监控条尺寸策略、保存位置、鼠标穿透与不抢焦点行为。
- 保留现有按需采样、单工作者、代际失效、后台暂停及资源释放机制。
- 保留进程操作的终止确认、同一句柄上的 PID/创建时间/退出/critical/protection 校验和安全性不确定时拒绝操作。
- 保留名称与 PID 的包含匹配、名称不区分大小写、忽略查询首尾空格、现有排序方向及不可用值排在真实零之后的规则。

### 本批不做

不全面改外观、不重写采样架构、不新增监控类别或常驻服务、不增加新的进程操作、不调整温度检测或驱动信任策略、不新增依赖、不升级框架、不改发布工作流、不提高版本号或发布新版本。

已经完成的温度性能验收不重开。没有新测量依据时，不宣称当前产品存在 CPU、内存或响应性能故障。

## 2. 调查依据与方案选择

以下为基线代码与既有测试的静态核对，不是本轮运行时缺陷复现或新版本性能结果：

| 依据 | 改进意义 |
| --- | --- |
| `MonitoringViewModel.SearchQuery` 每次赋值同步调用 `ProcessesView.Refresh()` | 可避免等效查询重复筛选，并合并快速输入 |
| `ProcessCountText` 只使用完整表的行数 | 筛选后缺少匹配数量反馈 |
| 进程页没有独立的加载、空列表、无匹配或读取失败提示 | 需要可测试的呈现状态，而不是依赖概览页的错误文本 |
| 采样异常时快照为空，旧表和选中项可能保留 | 必须明确旧数据状态并关闭新操作入口 |
| 每次进程快照 reconcile 后无条件刷新视图 | 可按成员、筛选字段和当前排序字段的实际变化决定是否重建 |
| 表已按 PID 和创建时间复用/替换行，行已按字段差异通知，DataGrid 已启用虚拟化 | 保留这些机制，不把已有功能计作新优化 |
| 操作服务已有真实身份与保护校验，窗口已在确认前捕获目标 | 只补充呈现层有效性门槛，不替换服务层安全边界 |

选择“现有工作流的小批改进”。先全面改外观会扩大范围且不能直接解决异常反馈；先重写采样架构缺少新的性能故障依据，回归成本更高。本批不采用这两种路线。

## 3. 组件边界与兼容性

| 组件 | 本批职责 | 不承担的职责 |
| --- | --- | --- |

| `MonitoringViewModel` | 在 UI 线程协调状态、查询、一次性合并、视图刷新、计数及选择有效性 | 不增加采样队列，不在搜索中调用硬件采样 |
| `MainWindow` / 监控样式与文字 | 呈现状态，提供清空和 Esc，绑定操作门槛，并在操作发起点重新检查 | 不通过界面检查替代真实身份与保护检查 |
| 现有 `MonitoringPump` / `MonitoringSession` / `ResourceMonitor` | 继续提供串行、按需、可失效的资源快照 | 不因本批搜索和呈现需求改变采样接口或温度后端 |

`ProcessesView` 仍为现有 WPF 集合视图。可以在现有集合类型内部合并成员变更通知；不引入其他表格库或新的应用级调度框架。

## 4. 呈现状态与数据生命周期

进程数据是否成功，与 CPU/GPU/温度单项是否可用分开判断。收到当前有效的非空资源快照即代表本次进程列表读取成功；列表本身允许零行。整个采样抛异常或未返回资源快照才进入进程读取失败状态。

| 状态 | 条件 | 展示与操作 |
| --- | --- | --- |
| 非活动 | 主窗没有可见进程页消费者，包括离页、隐藏、最小化、紧凑模式或关闭 | 清空行和选择，停止搜索合并；不保留进程历史，不增加后台工作 |
| 初始加载 | 进入可见进程页，尚未收到本会话成功列表且没有读取失败 | 显示“正在读取进程列表…”；匹配数和总数显示“—”，不显示成功空列表文案；操作禁用 |
| 正常 | 当前成功列表总数大于零，匹配数大于零 | 显示匹配数/总数；仅有效选中项可进入操作 |
| 成功空列表 | 本次成功列表总数为零，不论查询是否为空 | 显示“当前没有可枚举进程”；操作禁用 |
| 无匹配 | 成功列表总数大于零，但应用查询后匹配数为零 | 显示“没有匹配的进程”；保留清空入口；操作禁用 |
| 失败，无旧数据 | 本会话没有成功列表且读取失败 | 显示读取失败与可用诊断，匹配数和总数显示“—”，不声称总数真实为零；操作禁用 |
| 失败，有旧数据 | 本会话曾成功，后续读取失败 | 保留最后成功行，显著提示“显示上次成功数据；操作已暂停”，清除此前选择；操作禁用 |

失败提示优先于成功空列表或无匹配提示。旧数据可以继续用于本地查看、搜索和排序，但始终带过期标记；这种本地操作不能把失败状态变成正常。

再次收到成功快照后更新列表、清除失败状态并恢复正常选择能力。失败后首次成功应用时清除所有旧数据选择，包括失败期间仅用于查看的选择；不自动恢复失败前的选中项，用户需从成功列表重新选择。连续失败仅更新当前诊断，不积累历史列表或异常对象。

进入新进程消费会话时先应用最新有效查询，再请求现有采样；会话外不保存成功列表。搜索原始文本与排序偏好可以继续保留在现有视图模型的内存字段中，不新增持久化设置。

工作线程和 UI 应用快照时均保留现有 generation 检查。旧 generation 的成功或失败不能覆盖新会话状态。单项读数不可用仍按现有 `—` / 不可用规则展示，不把它误判为整张进程表失败。

## 5. 搜索、清空与一次性合并

### 原始文本与有效查询

搜索框立即保存原始输入；筛选使用独立的有效查询。有效查询是原始文本去除首尾空格后的值，等效判断与名称匹配一样不区分大小写。保留现有 PID 的十进制包含匹配，不增加正则、额外筛选语法或搜索历史。

- 新有效查询与已提交查询等效：更新原始文本和清空按钮，取消待处理合并，不重筛、不重排、不采样，并按当前数据状态恢复操作门槛。
- 新有效查询与当前待提交查询等效但不同于已提交查询：只更新原始文本，不重新启动等待，不产生额外刷新。
- 新的非空有效查询不同于已提交及待提交查询：采用 **150 ms** UI 线程一次性合并；新有效查询重置等待时间，仅提交最后的有效查询。
- 等待期间，表格与计数仍使用已提交查询，并显示“正在筛选…”；操作入口暂停，防止对与当前输入不一致的旧结果发起操作。若同时读取失败，失败/过期提示优先，不能被筛选提示隐藏。
- 空查询立即提交；清空按钮和 Esc 也立即清空，取消待处理合并，恢复完整列表。
- 采样快照在等待期间到达：仍按已提交查询处理；不能绕过合并提前使用原始输入。

合并使用仅在待处理时启动的短时 Dispatcher 回调/计时器；禁止新增常驻轮询。回调应校验消费会话及释放状态。离页、隐藏、最小化、紧凑模式和 Dispose 取消待处理工作；已排队但被撤销的回调不得更新表格。再次进入进程页时直接使用保留的最新文本，不重放旧回调。

### 清空入口与键盘

搜索框旁提供可键盘访问的清空按钮，有本地化文字或可访问名称。原始文本为空时禁用；只有空格时仍允许清空。

Esc 仅处理进程搜索框内的清空行为，不新增窗口级 Escape 拦截，不改变其他输入框、模态确认或现有关闭行为。清空后保留搜索框焦点。

## 6. 快照批量更新与条件刷新

每份成功快照在一次 UI 应用批次内完成行维护、视图处理、计数和选择检查。行身份仍为 PID 与创建时间；同一身份原地更新，创建时间改变替换行，消失的行删除，不保留退出历史。

变更摘要区分成员变化、名称变化和各数值字段变化。是否重建按当前已提交查询与当前排序字段决定：

| 变化 | 整表视图重建要求 |
| --- | --- |
| 完全相同快照 | 0 次；保留已有行，无多余行通知 |
| 仅非排序数值字段变化 | 0 次；只更新对应单元格通知 |
| 当前排序字段变化 | 最多 1 次；排序必须反映新值 |
| 名称变化，当前按名称排序或有效查询非空 | 最多 1 次，以保证排序/匹配正确 |
| 名称变化，当前既不按名称排序也无有效查询 | 0 次；只更新名称单元格 |
| 添加、删除或替换身份 | 合并成员通知，最多 1 次完整视图重建 |
| 查询实际提交或用户切换排序 | 每次提交/排序操作最多 1 次重建 |

成员批量变更可以向集合视图发出一次合并 Reset；如果它已经使视图重建，不得再无条件调用 `Refresh()`。仅使用 `DeferRefresh` 包裹后继续逐行触发全表工作，不算满足批量验收；以实际视图 Reset 和排序器调用测量为准。

成员、排序、筛选同时变化时仍合并为一次成功快照应用，而不是每种变化各刷新一次。新行与消失行的最坏情况通知不能随行数变成多次整表重建。

保持现有行/列虚拟化和 recycling。不通过减少完整进程列表、丢弃有效排序或把不可用读数当零来获得性能数字。

## 7. 选择有效性与操作门槛

`SelectedProcess` 与是否可以操作分开处理。有效操作目标必须同时满足：

1. 当前仍有可见进程页消费者，视图模型未释放。
2. 本会话最近一次进程快照成功，当前没有读取失败或未提交查询。
3. 目标仍属于当前表，PID 与创建时间和当前行相符，身份字段足以供服务验证。
4. 目标符合已提交查询且不是已退出/被替换的旧行。
5. 窗口没有正在执行的另一项进程操作。

在正常刷新和查询提交后，同一身份且仍可见的选择可以保留；目标被过滤、删除或创建时间改变时清除选择。集合 Reset 如果暂时清空 WPF 选择，只能恢复本次仍然有效的原行，不得按 PID 选择替换身份。

读取失败时立即清除此前选择。旧数据的后续视觉选择只能用于查看，不能启用操作；成功恢复后不得自动执行任何先前请求。

按钮禁用只是反馈，不能作为唯一保护。操作发起点再次验证上述门槛。终止仍在打开对话框前捕获明确目标，用户取消不执行；确认后、后台操作入队前重新检查该目标仍属于当前成功且可见的数据。若确认期间读取失败、目标消失/身份改变、查询排除目标或离页，应拒绝这次新操作并给出本地化提示。

已经进入后台的操作不承诺强制撤销；服务仍对保留的真实句柄验证身份、退出及保护状态。UI 新门槛不能取代、放宽或移除 `ProcessActionService` 的任何已有安全检查。所有自动测试使用原生替身或取消确认，不释放或终止真实用户进程。

## 8. WPF 呈现与本地化

- 有本会话成功列表时，顶部计数统一为匹配数/总数，例如“匹配：3 / 总数：500”，英文为“Matches: 3 / Total: 500”；成功零行显示 0/0，首次成功前显示“—”。旧数据计数必须和过期提示同时展示。
- 初始加载、成功空列表和无匹配在表格区域呈现，不能让空表含义依赖猜测；读取失败提示在保留旧行时仍可见。
- 状态与操作结果分别绑定；本次读取失败不能被上一次操作成功文本遮盖。
- 诊断原因保留为原始文本，在本地化前缀之外展示；使用换行、裁剪或提示框避免长错误撑大窗口，不因状态文本改变已有主窗最小尺寸。
- 新文字通过现有 `MonitorText` 提供中文、英文与非中文语言的英文 fallback；不改写已有语言包。
- 语言切换更新计数、状态、清空入口和拒绝提示，但不重筛、不重排、不改查询、排序、选择或持久化设置。
- 保持现有主题颜色资源与视觉风格，不新增动画、字体下载或图像资源。

## 9. 验收与证据要求

### 功能与故障回归

新增回归先针对基线证明当前缺口，再进行实现。至少覆盖：

- 名称/PID、大小写、首尾空格、空查询、等效查询、无匹配、成功零行、清空与 Esc。
- 20 次相邻约 10 ms 的快速输入后，等待静止期只提交最终查询，最多一次查询引起的视图重建；相同有效查询零次。
- 初始加载 → 成功、初始加载 → 失败、成功 → 失败 → 恢复，以及失败期间本地查询/排序不解除过期状态。
- 无资源快照与单项 CPU/GPU/温度不可用的区别。
- 相同行保留、退出删除、PID 复用替换、筛选排除清除选择、批量 Reset 后有效选择保留。
- 失败/筛选待处理/离页期间按钮与直接操作入口均拒绝新操作；模态确认期间目标变化或失败后不能入队执行；取消确认零次原生操作。
- 既有自保护、关键进程、权限失败、未知保护、同一 retained handle 验证和结果诚实性测试仍通过。
- 离页、隐藏、最小化、紧凑模式及 Dispose 取消合并且不重放失效回调；搜索不增加资源采样次数。
- 中文、英文和英文 fallback；语言切换不改变查询/排序/选择，不额外重建视图。

### 定向界面工作与响应测量

使用同一台机器、同一受控输入和相同测试宿主，对修改前后分别测量 **500 行与 2000 行**。不访问真实温度硬件，不执行进程操作，不把外部测试宿主描述成生产 App 启动测量。

场景包含完全相同快照、只变非排序指标、变排序指标、批量成员变化和快速搜索。快照场景各预热 10 次并记录 60 次应用；搜索场景记录 10 组快速输入。记录实际视图 Reset、排序器调用次数、UI 处理耗时及最终结果。按行数与场景分别计算 p95，采用排序后第 `ceil(0.95 × N)` 个样本，使用 Stopwatch 单调计时；不将不同场景混合以掩盖慢路径。

优化后的硬性标准（基线保留原始结果，不要求基线已经满足新行为）：

- 相同有效查询与完全相同快照：0 次整表重建；非排序指标单独变化：0 次。
- 每份成员/排序相关变化快照：最多 1 次整表重建，最终成员、计数和排序正确。
- 快速搜索合并后的最终结果正确，等待仅来自规定静止期与实际 Dispatcher 调度，不存在丢失最终输入的回调。
- 两种规模下，UI 快照应用、搜索输入处理和实际查询提交处理的分场景 p95 均不超过 **50 ms**；150 ms 合并静止期单独记录，不混入处理耗时，同时保留最后输入到最终结果的端到端时间。
